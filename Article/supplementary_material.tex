\section*{S2. Root of Trust Validation Incident Log}
\label{sec:incidentlog}

This section gives the full discovery-and-fix history behind three of the seven M2 maintenance moments summarized in Table~S8, row 7.1.4 -- the PUF/NVS reliability and security fixes (Incidents 1--3 below) and their FT-06 re-validation (Incident 4) -- not the enrollment-state-confusion bug, the forward-secrecy fix, the WiFi-provisioning fix, or the per-device \texttt{id\_a} fix, which are covered directly in the main text. It is provided for completeness and independent reproducibility; the main text states only the final, corrected state of the firmware and the headline bench results.

\textbf{Incident 1 --- raw PUF measurement left in NVS.} \texttt{esp32\_puflib}'s enrollment procedure (\texttt{provision\_puf\_calculate()}) wrote a \texttt{PUF\_FREQUENCY} blob to NVS --- the per-bit frequency count across the 20 deep-sleep-path enrollment measurements --- and never erased it, contrary to the paper's claim that no raw PUF response is ever written to flash: that blob is sufficient to reconstruct the stable-bit mask and PUF reference without the physical device. The fix overwrites it with zeros and erases it (\texttt{nvs\_erase\_key()}) once the stable-bit mask and ECC helper data have been derived from it; this does not change the derived key, so it did not by itself require re-enrolling an already-provisioned device. The fix does not fully guarantee physical removal: ESP-IDF's NVS is a log-structured store that alternates between two versions of a blob on every write, so the zero-overwrite only scrubs the \emph{most recent} version. A raw dump taken immediately after a standard enrollment (before any further provisioning) showed the complete, un-zeroed 20-measurement table from an earlier version still present and byte-recoverable, logically marked erased but not yet overwritten (NVS only reclaims that space when it later garbage-collects the page). SMG\_NODE\_01's NVS as currently deployed carries none of this residue (confirmed directly: zero \texttt{PUF\_FREQUENCY} entries of any kind in a fresh read-only dump), because its server reference was pinned by flashing a freshly generated NVS image that merges the provisioning namespaces with the four helper-data blobs read back from the device, rather than by the standard enrollment path alone; this was done with a one-off, hand-written firmware patch (code repository's \texttt{smg\_puf\_rot\_node} README, Provisioning caveat) that is not published as reusable tooling, so this specific provisioning method is not independently reproducible from the published repository as it stands. A freshly generated image carries no erased entries, which is a side effect of that provisioning method, not a property the library itself guarantees, so the residue described above should still be assumed present on any node enrolled through the standard path alone. Only flash encryption (ITER~2 candidate) closes this fully regardless of provisioning method.

\textbf{Incident 2 --- helper-data-manipulation oracle.} \texttt{PUF\_MASK}/\texttt{ECC\_DATA} (and their deep-sleep-retry counterparts, \texttt{PUF\_SLEEP\_MASK}/\texttt{ECC\_SLEEP\_DATA}) are legitimate public helper data under standard fuzzy-extractor constructions (the device's 8$\times$-repetition code is a code-offset secure sketch), but they are stored in NVS without integrity protection; an attacker with physical write access to this same chip's flash could manipulate them and use the ECC decoder's error count (surfaced via diagnostic logging needed for this work's own bench measurements) as an oracle on individual response bits. The fix binds SHA-256 of all four helper-data blobs into the HKDF info used to derive $(sk_A, pk_A)$, so manipulating any of them changes the derived key unpredictably instead of the key itself leaking information. This was applied in two passes: the first bound only \texttt{PUF\_MASK}/\texttt{ECC\_DATA} (the first-attempt/RTC path); a second, independent review found that the deep-sleep-retry pair was left unbound, leaving the same oracle exploitable via that path, so the hash was extended to cover all four blobs. A direct single-bit-flip test on each of the two retry-path blobs (leaving the other three blobs and the physical PUF untouched) confirmed the extended binding is genuinely load-bearing: the server rejected the device's signature both times, while first-attempt reconstruction (which never reads those blobs) kept reporting a normal error rate; restoring the unmodified image immediately re-established a successful handshake. This is a narrower guarantee than ``closes the oracle'': the error-count value is computed and logged \emph{before} the HKDF binding is applied, so an attacker able to observe that diagnostic output (not just the handshake's success or failure) over UART still learns something about which bits were manipulated, independent of what key eventually gets derived from them; a production deployment should compile that diagnostic out, which this TRL~3 validation firmware deliberately does not do. The binding also does not substitute for secure boot or flash encryption (ITER~2 candidates): an attacker with write access to this chip's flash could instead replace the firmware itself with one that reads and transmits the reconstructed response directly, bypassing the derivation entirely. Each of the two binding passes changes the derived key, so each required re-enrolling SMG\_NODE\_01 and re-registering the resulting $pk_A$ with the server; both re-validated end-to-end ($N=30$, 30/30, Table~17 main text) and against FT-06 (rejected in all attempts, see Incident 4 below).

\textbf{Incident 3 --- miscalibrated local reliability gate.} \texttt{esp32\_puflib}'s own reliability gate originally combined a hamming-weight sanity check with a raw bit-error-rate threshold (0.15\%). An intermediate bench round run under this unrelaxed gate (\texttt{bench\_results\_20261015/}) returned 0/30 end-to-end success, every trial timing out: across 180 first-attempt measurements, raw bit-error rate ranged 0.455--0.760\% (mean 0.589\%), and across 150 retry-path measurements, 0.226--0.406\% (mean 0.329\%) --- both consistently above the 0.15\% figure on both reconstruction paths, so every attempt was rejected locally before a handshake was ever attempted. On inspection, this gate turned out not to be a security boundary: \texttt{correct\_data()} already runs the measurement through the 8-bit majority-vote repetition code regardless of the error count, producing its best-effort reconstruction either way, and a wrong reconstruction simply fails the server's ECDSA verification downstream, exactly like any other incorrect answer. The gate was therefore relaxed to a diagnostic, keeping only the hamming-weight sanity check (a raw-randomness check unrelated to matching any specific enrollment) as a hard gate. This fix does not change the derived key and did not require re-enrollment.

\textbf{Incident 4 --- cross-chip cloning re-validation (FT-06) across firmware generations.} To confirm none of the three fixes above changed the cross-chip detection guarantee, the FT-06 test (cloning SMG\_NODE\_01's entire NVS onto SMG\_NODE\_02's physical hardware and attempting reconstruction) was repeated after each firmware generation, for 11 attempts in total, all rejected by the server: the original firmware (1 attempt, 29.9\% device-side error, accepted unchecked on the retry path since that firmware version applied no threshold there at all); the error-rate-relaxed firmware (4 attempts, 29.8\% error, no retry triggered since the relaxed gate now locally accepts it on the first attempt); the first-generation helper-data-manipulation mitigation (3 attempts, $\sim$29.9\% error each); and the mitigation extended to all four blobs (3 attempts, 29.77--29.79\% error each). Device-side error stayed essentially constant (29.8--29.9\%) across all four generations, confirming that what changed across these fixes was whether and when the device locally accepts a reconstruction, never whether the server ultimately detects a wrong one.

\textbf{Resulting bench rounds.} Each stage of this incident log produced a fresh $N=30$ bench round: \texttt{bench\_results\_20261015/} (0/30, Incident 3's unrelaxed gate, same identity as the round before it), \texttt{bench\_results\_20261015\_fixed/} (30/30, Incident 3's gate relaxed; same identity still, since that fix does not change the derived key), \texttt{bench\_results\_20261015\_hdm/} (30/30, Incident 2's first-generation two-blob binding, which does change the derived key -- re-enrolled), and \texttt{bench\_results\_20261016\_hdm2/} (30/30, Incident 2's binding extended to four blobs, re-enrolled again -- the twice-corrected identity reported as the canonical round in the main text). All are deposited in the companion artifact repository (Materials Availability) and kept for provenance even though superseded.
